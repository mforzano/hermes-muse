# Role-scoped briefings

Use this procedure for a user-requested daily or periodic overview. The subscription determines the schedule and scope. It is separate from patrols that interrupt only for worthwhile changes. Use the existing native Cron when updating an existing report, preserving its ID, schedule, model, destination and pause state. Do not create a second subscription or silently import unrelated jobs. Installation itself creates only the six fixed Muse jobs; a subscribed report is a user-managed native Cron using this Skill, not an entry in muse/install.json.

Load the communication and source-checking procedures. Apply [proactivity Coverage scope](proactivity.md#coverage-scope) before discovery; the requested report scope does not widen profile duties or permissions, and excluded sources are not missing coverage. Read muse_manage context, relevant native memory, current user preferences and recent user-facing results. Discover the in-scope authorized sources and their connector Skills. Mail, calendars, reminders, task stores, notes and devices are inputs when included in the coverage plan and actually connected; no named provider, application, account or local path is required. Existing local source notes may locate an account or task collection, but do not inherit an old digest's ranking, sampling or formatting rules. Read-only inspection within this established scope needs no fresh confirmation.

Establish the report's current date, timezone and coverage window. For a rolling 30-day or this-month calendar component, load the [calendar procedure](calendar.md), use calendar_window/calendar_view and their independent source resources; preserve original all-day calendar dates as well as profile timezone overlays. Check relevant collections/accounts and pagination; distinguish absent connections, failed checks and successful empty results. Reuse recent evidence with its source and observation time where still sufficient; recheck mutable or time-sensitive facts before relying on them. Parallelize independent reads where supported. Work through the useful sources rather than using a fixed tool-call, line-count or first-item quota. Record source_check using stable source identities and honest expected/checked coverage, following proactivity. Missing pages or collections leave that source partial and cannot advance its success watermark.

For mail, use metadata to identify potentially meaningful threads, then read their bodies and relevant replies to determine the change and whether the user needs to act. Preserve subject, sender, account, time and a stable message/thread locator or link. Pass message IDs exactly as listed, in full (Apple Mail uses the whole RFC 2822 Message-ID); never a sender address or an ID fragment, and do not retry an ID that returned not found: search once instead. An importance label, unread count or title alone is not an action judgment. For events/reminders/tasks, inspect original dates, status, notes and context; retain literal titles in source evidence (use communication.md for the outward wording) and distinguish stale overdue entries from current commitments. An old overdue date is not automatically today's highest priority. Resolve ambiguous identities through sources or conversation evidence before guessing their meaning.

## Goals in progress

For a daily or periodic overview, call `muse_manage context {section:"goal", status:"attention"}` and follow `next_cursor`. It returns only active goals that need a line: waiting for the user, blocked, a next check missed by more than an hour, no progress entry for three or more days, or progress recorded in the last day. Each row carries `attention: {reasons, waiting_on, idle_days, last_progress_at}`. When it returns no items, leave the section out entirely; never list every active goal. Otherwise write one short section: first the goals with `waiting_user`, marked as waiting for the user, then the rest. One line per goal: its literal title, what it waits on or is stuck on (`waiting_on`: the user, the blocked reason or the owner; for a goal that only changed, the latest progress in a few words) and how long it has not moved (`idle_days`; 0 means today). Open a goal body only when that line would otherwise mislead. This section is read-only: the briefing does not update goals, move next checks or create notices for them; a stalled goal that needs action goes to the parent conversation through the normal flow.

Synthesize what affects the user's day: commitments, conflicts, deadlines, substantive changes, useful preparation and decisions. Rank by evidence-backed impact, timing and actual user context. Do not prescribe busywork from counts or force every report into fixed sections. The content determines the length; keep useful detail, original-source links and material uncertainty. Complete readily available follow-up reads before handing off. A concrete blocker can leave a limited judgment open, with the failed check and consequence stated honestly; a sparse summary cannot.

Compare against recent actual user-facing replies, current notifications and prior report outputs. Do not reissue unchanged mail/news as a fresh alert, recreate notification candidates for information delivered by this report, or mistake a queued packet for a delivered reply. A subscribed overview may briefly identify a still-relevant commitment already mentioned, with its current status. The patrol checks conversation outcomes before any later notice. Source checks are evidence, not proof of user awareness. A quiet day still receives the agreed report, including an honest short all-clear when checks succeeded; missing data never becomes an all-clear.

Write the report text before any bookkeeping. For a subscribed report, source_check, notes and notices are optional evidence, never a delivery precondition: send one call of a new shape before batching copies, correct it at most once using the usage the error returns, then mention the gap in one sentence and deliver. Repeated failing tool calls can make the host stop the turn and replace the whole report with a stop message.

Deliver the report as this existing Cron's final output to its configured destination. For Bot Chat, retain enough findings and source locators for the receiving assistant to give a self-contained answer and finish any necessary authorized lookup. Do not call notification_prepare, create a delivery-only Cron, send an extra message or mark delivery successful yourself. Subscribed reports are not subject to opportunistic-notice silence rules. Native execution/output/delivery history remains the record; do not call run_complete/review_complete with an invented fixed-job name.

When changing or ending the subscription, update or pause/remove that same native job. Plugin upgrades do not rewrite user-managed report schedules or prompts. Before removing the plugin, find native reports using hermes-muse:companion as well as owned jobs; pause/remove those reports or explicitly convert them to standalone instructions as the user requests. Preserve user data and unrelated tasks. Source retrieval never authorizes sending mail, editing external tasks, changing calendars or renewing a monitoring subscription.
