# Bounded context and checkpoints

`muse_manage(action=context|status,data={})` returns a small directory, not all objects and not evidence that collections are empty. Follow its sections and refs. The 256 KiB response ceiling is a plugin transport/work budget, not a model-context size or authorization rule. Do not raise it, clear history or guess limit/view fields to recover.

`task_runs` gives bounded references to each job's active attempt, latest ended result and last complete result. Open the matching run with content_read before claiming recovery. `signal_reviews` reports each independent processed_through, pending count and oldest_pending; a recent scheduler exit or note file does not clear a stalled signal prefix. Compare these checkpoints with the preceding run and real incoming evidence; preserve a consequential stall through the existing finding/notice flow. Operation checkpoint IDs are not event counts or throughput measurements.

- Collections: `context {section:goal|feed|interest|idea|notice|run|source_check|finding|research,limit:25,cursor?}`. Follow next_cursor until null. Open each relevant ID using content_read for its body/metadata. Lists are revision-bound: cursor_expired means reread that section, not continue combining snapshots. No read-status is stored.
- Large object metadata: when metadata_complete=false, follow metadata_ref. It returns explicitly labelled JSON metadata text in body pages. Keep its revision, concatenate all pages, then interpret the complete JSON; an individual chunk is not a complete record. Normal Markdown body paging remains separate.
- Conversation evidence: `context {section:conversations,limit:25,cursor?}` lists descriptors, not transcript bodies. For each required session, call conversation_read with its session_id, revision and next_offset. Continue until complete; notice review needs only each session's newest 24,000 characters, which next_offset targets. Call conversation_read with session_id alone (or descriptor=true) for a fresh descriptor. A change returns available=false with the current revision/next_offset: unchanged exact prefixes retain coverage, new/changed text must be read. Recheck current descriptors/revisions before notification_review. Children use read_only=true for history; their reads do not certify parent notice coverage. Quiet-hours, relevance review and actual transport receipts remain separate.

## Signal review window (maintenance parent)

1. Hourly intake opens `context {section:signals,job:memory-upkeep}` and keeps its window. The scope mixes old pending and new signals; backlog is separate.
2. Use `{section:signals,job:memory-upkeep,window,ids:[...]}` for batches of short bodies, or id/offset/length for long originals. A batch may return an individual gap without blocking other IDs. Follow each returned next_offset; an index or excerpt is not review.
3. Save actual facts/decisions and call `review_complete {job:memory-upkeep,window,ids:[actually processed IDs],summary}`. Only complete served originals can receive a revision-bound upkeep marker. Old unread signals remain and cannot be crossed by the continuous timestamp cursor; later processed IDs will not be reprocessed.
4. A changed selected original invalidates that scope. Unselected history is still pending, not certified read. Nightly has no second intake queue: `signals` with job=nightly-review gives synthesis guidance; a specific id reads original evidence without processing it.

## Revisions, findings and retries

Goals use their integer metadata revision for optional expected_revision. For all other objects, copy revision strings verbatim from tool data. Do not retype, normalize or reconstruct them. revision_conflict means reread and merge; retrying a mistyped value cannot recover. A new logical merged request uses a new request_id; replay the same exact logical request with the same key when its result is uncertain.

A request_id is unique to every run: build it from the action, this run's start time to the minute and the object or source (`source_check-20261023T1205-mail-inbox`), never from the date alone. A job that runs several times a day sends different arguments each time, so a key reused from an earlier run or from the same day fails with idempotency_conflict. The conflict error returns `suggested_request_id`: resend the same arguments under it (refresh expected_revision if a revision error follows). Only an exact replay of one call, after an uncertain result, reuses its key.

Create finding_record with expected_revision="absent", a unique request_id, evidence and the required finding fields. For a new finding omit id: the service derives it from returned operations evidence refs. For an existing finding, first content_read(kind=finding,id), then use that revision. An unavailable object is not a reason to omit the create revision. A finding reports evidence; closing it still needs verification and disclosure or a no_notice_reason.

A successful oversized mutation may return result_is_reference/content_ref. It has committed: read the reference; do not repeat the mutation with a new key. Context overview and collection reads no longer reconcile notifications; actual notification actions retain their normal lifecycle checks.

### Final tool response and recovery

Every action validates the whole request (512 KiB, nesting and control-token bounds) before journal, track, bind or dispatch. Oversized content/question/watch input is rejected before work. `window` belongs only to memory-upkeep/nightly-review. The final 256 KiB envelope includes revision/recovery fields and errors.

Argument errors are written to be acted on. Each `ok:false` result names the action and field path (`data.query_window`), what was expected, what arrived (type and a short clipped value), and the exact repair (for example "move data.account and data.connection into data.source" or "this is not a calendar source: delete data.query_window and put the time range in data.scope"); common ones add `field`, `expected`, `received`, `hint` and a minimal `example`. A misplaced field gets its correct location; other unsupported fields list the action's allowed fields. Interpreter exceptions (`KeyError`, `TypeError`, `AttributeError`) never reach the caller: the single entry point converts them to `invalid_argument` with the action, field and schema hint. `retryable` is true only when resending after the stated correction can succeed (revision_conflict, revision_required, cursor_expired, source_unavailable); every other validation error says that an unchanged resend fails again. Codes and success results are unchanged.

Committed large results use `result_is_reference/content_ref`; large native errors remain `ok:false` with a bounded reason and `error_ref`. Follow these refs with `content_read`; retain revision and concatenate body pages before interpreting the JSON. `kind=tool_result` is an immutable exact tool envelope in existing profile records, accessible only by its originating private session and ID (no collection or Dashboard exposure). It does not authorize a side effect, certify served conversation evidence, or claim native task completion. Ordinary object references still use their existing domain access. Pure reads do not create receipt records; invalid input is rejected with a bounded explanation.

The following actions additionally accept an optional `request_id` (1..128 characters): delegate, research_start, research_status, watch_stop, operations_read, operations_batch, operations_complete, operations_commit, review_complete, run_complete, notification_prepare, notification_queue, notification_handoff. Use it for a logical state-changing call; identical arguments/key return its exact completed receipt. A key with changed arguments/origin is rejected. A pending/interrupted call returns outcome_unknown without repeating work; inspect native evidence or its existing checkpoint, never create a new key to redispatch unknown execution. This reuses mutation_request, releases the lock during native work, and does not replace CAS or existing own content/install journals. Calls without a key retain their existing recovery contract and must not be blindly retried.

`research_start` large results reference the saved research object; `research_status` may reference the exact observed envelope. Both can be fully read via content_read pages without another dispatch. An allocation receipt (operations_read/batch) is not substantive review: read its refs and actual evidence before committing a checkpoint.
